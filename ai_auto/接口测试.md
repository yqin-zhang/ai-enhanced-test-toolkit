# 设备管理接口测试用例

被测服务：`test_projects/device_server.py`  
Base URL：`http://127.0.0.1:8000`  
文档页：`http://127.0.0.1:8000/docs`

约定：

- 正向业务成功：HTTP 200，body 含 `code = 0`
- 业务错误：400 / 404 / 500，body 含 `detail`
- 入参校验失败（Pydantic）：422
- 方法不允许：405
- 状态枚举仅允许：`online` / `offline` / `fault`
- 注册字段约束：`device_id` 1~64，`device_name` 1~128，`device_type` 1~64
- 列表接口 `data` 为数组；单条查询 `data` 为对象
- **字段类型修正**：字段值为数字 / `null` / 布尔 / 数组 → 422 `string_type`；顶层 body 非对象（数组、数字、字符串）→ 422 `model_attributes_type`。
- **额外字段默认忽略**：多传字段不影响注册/改状态，仍 200。
- **字符串不做 trim**：前后空格、纯空格（长度达标）都按原值接收。
- **Content-Type 必须是 `application/json`**：不发 Content-Type 或发 `text/plain` / `application/x-www-form-urlencoded`，即使内容是合法 JSON 原文，也按字符串处理 → 422 `model_attributes_type`。
- **尾斜杠**：在已定义路由后加 `/` → **307** 重定向到无斜杠地址（无响应体）；`requests` 默认自动跟随重定向，断言 307 必须设 `allow_redirects=False`。
- **HEAD / OPTIONS / PATCH 等未实现方法**：统一 405，且实测 **HEAD/OPTIONS 没有自动支持**（无 CORS 中间件），405 带 `Allow` 头（如注册接口返回 `Allow: POST`）。
- **大小写敏感**：路径段和状态枚举均精确匹配。`GET /device/LIST` 被当成查 id=`LIST` → 404「设备不存在」；状态 `ONLINE` → 400。
- **路径参数 `device_id` 无长度/字符约束**：200 字符 id、SQL 注入串、emoji、点号、空格（编码后）都能匹配路由，设备不存在时统一 404「设备不存在」。
- **状态更新校验顺序**（源码 [device_server.py](../test_projects/device_server.py) 实测）：Pydantic 类型校验（422）→ 状态白名单（400）→ 设备是否存在（404）。因此不存在设备 + 非法状态 → **400 而非 404**；不存在设备 + 数字状态 → 422。

建议：需要设备的用例自行注册/清理（夹具），不要依赖跨文件执行顺序。

约定补充：`GET /device/{device_id}`、`DELETE /device/{device_id}` 会吃掉 `/device/` 后任意一段。因此 `GET/DELETE /device/lists` 是「设备不存在」，不是框架 `Not Found`；`Not Found` 只出现在前缀都不匹配的路径（如 `/devices/list`、`//device/list`、`/device` 无尾段、`/mock/SERVER500`）。列表的 405 只测 POST/PUT/PATCH/HEAD，不要测 DELETE `/device/list`。注册的 405 不要测 GET `/device/register`。

> 编号说明：原有编号保持不变；同一场景多个参数化取值用 `a/b/c` 拆分（每行 = 1 条可执行用例）；每个接口现有用例之后追加的为**新增用例**，编号续接。全部预期均已对运行中的服务实测确认。

| ST-N20 | 异常 | 顶层 body 为数组 | 设备存在 | `json=[{"status":"online"}]` | 422；`model_attributes_type` |
| ST-N21 | 协议 | 表单提交 | 设备存在 | status 走 form-urlencoded | 422；`model_attributes_type` |
| ST-N22 | 协议 | 不带 Content-Type 发 JSON | 设备存在 | `data=JSON字符串` | 422；`model_attributes_type` |
| ST-N23 | 协议 | `text/plain` 发 JSON | 设备存在 | Content-Type=`text/plain` | 422；`model_attributes_type` |
| ST-N24 | 协议 | 尾斜杠 | 设备存在 | PUT `/device/{id}/status/`，`allow_redirects=False` | 307；`Location` 指向无斜杠地址 |
| ST-N25 | 协议 | PATCH 方法 | 设备存在 | PATCH status 地址 | 405；`Allow: PUT` |

注意：

- 路径中的 `{device_id}` 必须与注册 id 一致（例如不要注册 `dev002` 却改 `dev001`）。
- 注册默认 `status=offline`。测改成 `offline` 时，须先改成其他合法值再改回来，否则 GET 仍是默认值，证明不了「已变」。
- ST-N03 / N04 / N05 / N14 / N15 / N16 走同一段业务校验（白名单 400），测试里可参数化合并；文档按取值拆行。
- ST-N06（`{}` 缺字段）和 ST-N07（整段 body 没传）都是 422，但 `loc` / `input` 不同，不要合成一条。
- 语法错误必须 `data=` 发原文；`json=` 会先被序列化，发不出去非法 JSON。
- ST-N11~N13 锁定校验顺序，防止后续把白名单和设备查询顺序调换后无感知。
